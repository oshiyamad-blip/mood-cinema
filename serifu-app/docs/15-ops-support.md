# 運用準備：負荷分散とサポート窓口

リリース後の「アクセスが増えたらどうなるか」と「問い合わせをどう受けるか」の設計。

## 1. 負荷分散の考え方 — サーバレス設計なので開発者側のスケーリング作業は不要

本アプリは**バックエンドを持たない**。ユーザーが何万人に増えても、開発者が
サーバを増強・負荷分散する必要がある箇所は存在しない。機能ごとの負荷の行き先：

| 機能 | 処理場所 | 負荷が増えたとき |
|---|---|---|
| 台本の解析・保存・練習履歴 | ユーザーの端末内 | 各端末で完結（合算されない） |
| 読み上げ（TTS） | 端末内蔵TTS | 同上 |
| 音声認識（ハンズフリー） | 端末内（高精度ONのみOSのクラウド認識） | OS提供元（Apple/Google）が負担 |
| 広告 | Google AdMob | Googleのインフラが負担 |
| アプリ配信 | App Store / Google Play | ストアのCDNが負担 |
| ポリシー・サポートページ / Web版 | GitHub Pages | GitHubのCDNが負担（静的ファイルのみ） |
| APK直接配布（テスト用） | GitHub Releases | GitHubが負担 |

つまり**スケールの心配が要らないことが、この設計の意図**（docs/01 参照）。
費用も増えない（AdMob収益はユーザー数に比例して増える一方、インフラ費はゼロのまま）。

### 唯一の例外と、その時の設計

「クラウド高品質音声」（`CloudTtsConfig` 設定済みビルドのみ・現在は無効）を
将来有効化する場合のみ、開発者管理のプロキシに負荷が集中する。その際は：

- **Cloud Run 等のオートスケールするマネージドサービス**で建てる（インスタンス
  上限を設定して費用の上限を先に決める）
- プロキシに**レートリミット**（端末単位・IP単位）と**日次コスト上限**を必ず入れる
- 落ちてもアプリは端末内TTSに自動フォールバックする実装を維持する
  （クラウド不通＝機能停止にしない）

この条件を満たせない間は有効化しない。

### 監視（週次でよい）

- ストアレビュー（App Store Connect / Play Console）— 不具合報告の最速チャネル
- Play Console「Android vitals」/ App Store Connect のクラッシュ統計
  （クラッシュSDKは入れていないため、OS標準の統計を見る）
- GitHub Pages の稼働（サポート/ポリシーURLが審査要件のため、
  リポジトリの Actions デプロイ失敗に気づけるようにする）
- AdMob ダッシュボード（表示回数の急変は不具合のシグナル）

## 2. 問い合わせ窓口の体制

### チャネル構成（一次解決で窓口自体を負荷分散する）

1. **アプリ内 FAQ**（設定 → サポート → ヘルプ・お問い合わせ）— まずここで自己解決
2. **公開サポートページ** `https://oshiyamad-blip.github.io/mood-cinema/support.html`
   — ストアの「サポートURL」に登録する。アプリを開けない人・入れる前の人向け
3. **メール窓口** oshiyamad@gmail.com — FAQで解決しない問い合わせの受け皿。
   アプリ内の「定型文をコピー」で、端末・OS・症状が最初から揃った形で届く
4. **ストアレビュー返信** — 不具合系レビューには返信でサポートページへ誘導する

FAQの文面は `lib/screens/help_screen.dart` と `web/support.html` の2箇所にある。
**片方を直したら必ずもう片方も直す**（メールアドレスは privacy/terms とも共通）。

### 運用ルール（1人運用の現実に合わせる）

- 返信目安：**数日以内**（サポートページにもその旨を明記済み。SLAを約束しない）
- Gmail 側の準備：
  - フィルタ「件名:【ホンヨミ】→ ラベル `honyomi-support`」を作る
    （アプリの定型文の件名が【ホンヨミ お問い合わせ】のため自動で仕分けされる）
  - よくある返信はGmailのテンプレート機能に登録（FAQへの誘導文＋個別回答）
- 優先度の目安：
  1. クラッシュ・起動不能・課金/広告の誤動作 → 即日調査
  2. 特定の台本形式が取り込めない → 形式を聞き、再現用の**合成台本**を自作して修正
     （ユーザーの台本原文は受け取らない方針。著作権・秘匿性のため）
  3. 要望 → リストに記録し、まとめて判断
- 問い合わせが月に数十件を超えて捌けなくなったら：Googleフォーム化
  （必須項目で情報の抜けを防ぐ）→ それでも溢れたらFAQの拡充を優先する

### 個人情報の扱い

- 問い合わせメールに含まれる個人情報（メールアドレス等）は対応目的にのみ使い、
  対応完了後も共有・公開しない（プライバシーポリシー7条の窓口として運用）
- 台本データは受け取らない。送られてきた場合は内容を利用せず、その旨を返信する
