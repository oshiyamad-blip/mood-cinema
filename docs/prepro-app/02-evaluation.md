# 検討：LLMで香盤が作れる時代に、アプリで出す意味

| 項目 | 内容 |
|---|---|
| 文書バージョン | 0.2（全面改訂） |
| 改訂日 | 2026-10-12 |
| 改訂の理由 | 敵対的レビュー（`08`）で、競争空白・「海外では5本に分断」・検索が空いている、という v0.1 の前提が崩れたため。価値の置き場所を「香盤を作ること」から「香盤を正しいまま回し続けること」へ移した |

## 1. 結論

台本から最初の香盤表を作ることは、もはや差別化にならない。一般のLLMに台本を渡せば、それらしい香盤表が出てくる。2026年6月には、それを製品にした「脚本パックン」も正式リリースされた。

アプリとして出す意味は、その先にある。香盤表は一度作って終わりではない。改訂稿が来る、俳優のNG日が変わる、ロケ地が飛ぶ、雨で撮影日が入れ替わる。そのたびに香盤表・総スケ・日々スケを食い違いなく直し、関係者全員に最新版を届け、誰がどの版を見たかを押さえる必要がある。この「変わり続ける香盤を、事故らずに回し続ける」仕事こそ、LLMの単発の出力では担えず、助監督が最も時間と神経を使っている部分である。

KOBAN は、香盤を生成する道具ではなく、**撮影準備の正本となる台帳**として作る。生成（LLMによる下書き）は中の部品の一つにとどめ、製品の中心は、変更の追従、根拠の提示、矛盾の検査、配布と確認、台本を安全に預かること、の5つに置く。

価値が大きいのは、改訂も関係者も多い現場である。最初の顧客は、縦型ショートドラマの量産現場と、配信向け連続ドラマの助監督部・制作部に絞る。年に一本の自主短編は、LLMに一度作らせて Excel で直せば足りるので、無料の利用者として受け入れる。

## 2. v0.1 から取り下げた前提

| v0.1 の前提 | 実際 | 扱い |
|---|---|---|

| 海外では5本の別アプリに分断されている | StudioBinder・CineFlo・Cadrage Studio はすでに統合型。リールの投稿者が5本すべてを使っている確証もない | 取り下げ。統合そのものは価値の根拠にしない |

## 3. LLMにできること、できないこと

一般のLLMに台本を渡して香盤表を作らせた場合と、撮影準備の実務が求めるものを並べる。

| 実務が求めること | 一般のLLMに台本を渡す場合 | 理由 |
|---|---|---|
| 最初の香盤表を作る | できる | 台本の読解と表の生成は得意分野である |
| 改訂稿のたびに、何が変わったかを示して直す | できない | 前回の出力を状態として持たない。作り直すと結果が揺れ、変わった箇所と揺れた箇所の区別がつかない |
| 香盤表・総スケ・日々スケを食い違わせない | できない | それぞれ別の出力になり、片方を直しても他方に伝わらない |
| 各印の根拠（台本のどの行か）を示す | 不確か | 尋ねれば答えるが、答え自体が正しい保証がない |
| 抜け漏れを止める（出番のある俳優が日々スケにいない、など） | できない | 正解の台帳がないので、照合する相手がない |
| NG日・拘束時間・ロケ地の時間の矛盾を止める | 不確か | 条件を与えれば指摘はするが、毎回の網羅は保証されない |
| 50人に最新版を届け、誰が見たかを押さえる | できない | 配布と確認の仕組みがない |
| 公開前の台本を安全に扱う | できない | 一般のチャットAIに台本を貼ることは、守秘義務の契約や制作会社の規則に触れうる |
| 電波のないロケ地で使う | できない | 通信が前提である |

この表の「できる」は一行だけである。そして実務で事故が起きるのは、二行目以降である。香盤表から俳優が一人抜け落ちれば、その人は呼ばれず、撮影日が丸一日飛ぶ。必要なのは、もっともらしい出力ではなく、検証できて、変更に追従する正本である。

## 4. 価値の所在：事故らずに回せる台帳

KOBAN の価値を、5つの柱と1つの接続口に分ける。要件定義（`03`）の優先順位はこれに従う。

### V1 正本
香盤表・総スケ・日々スケ・ショットリストは、すべて同じ台帳（シーン・要素・人物・撮影日）から導出する。どれか一つを直せば全部が変わり、食い違いが構造的に起きない。

### V2 変更の追従
台本の改訂、NG日の変更、ロケ地の差し替え、撮影日の組み替えを取り込むと、影響を受ける箇所を一覧にして見せる。変更は版として残り、いつでも前の状態に戻れる。現場で最も頻度が高く、最も手間のかかる作業を、ここで引き受ける。

### V3 根拠と検査
香盤表の一つひとつの印に「台本のどの行から来たか」「誰が手で付けたか」を残す。そのうえで、NG日・拘束時間・重複・抜け漏れを機械的に検査する。LLMの下書きを使う場合も、根拠のない提案は採用前に印が付く。

### V4 配布と確認
日々スケをリンクで配り、更新したら差分を添えて配り直し、誰が確認したかを集計する。キャストがスマホで自分の入り時間を読めることを最優先にする。

### V5 台本を預けられる場所
台本の本文を、解析の改善・統計・AIの学習・第三者への提供に使わないことを最上位の原則にする。さらに本文は端末で暗号化してから同期し、運営者にも読めない仕組みにする。競合もすでに「AI学習対象外」を掲げているので、約束だけでは差にならない。差になるのは、読めない仕組みのほうである。

### 接続口：LLMが作業する土台になる
LLMと張り合うのではなく、利用者がふだん使っているLLMから台帳を読み、変更を提案できるようにする。LLMからの変更は、人の変更と同じ検査（V3）を通り、提案として承認を待ち、履歴（V2）に残る。CineFlo がすでに Claude や ChatGPT との接続を出しているように、この方向は海外でも始まっている。

## 5. 誰にとって価値が大きいか

台帳の価値は、変更の頻度と関係者の数に比例して大きくなる。

| | 関係者が少ない | 関係者が多い |
|---|---|---|
| **変更が多い** | 自主の長編、低予算の連作 | **縦型ショートドラマの量産、配信の連続ドラマ**（主な顧客） |
| **変更が少ない** | 自主短編、学生作品（無料で受け入れる） | 単発のCM・MV（従たる顧客） |

縦型ショートドラマの量産現場は、同じロケ地で何話もまとめて撮り、台本の直しが撮影の直前まで続く。連続ドラマは話数をまたいで撮影日を組む。どちらも香盤表の作り直しが毎週起き、関係者は数十人になる。ここが、LLMの単発の出力では回らず、道具に払う理由が最も強い層である。

一方で、市場規模を示す数字には注意が要る。邦画の公開本数（2025年694本）は横ばいで、対象外の商業映画の数字である。縦型ショートドラマの市場予測は視聴の市場で、制作ツールへの支出ではない。想定顧客の数は、制作会社と助監督・制作部の人数から積み上げて、要件定義の KPI（`03` 第14章）で検証する。

## 6. 競合との位置取り

| | 最初の生成 | 正本・追従 | 根拠と検査 | 配布と確認 | 台本の秘匿 | 現場（オフライン） |
|---|---|---|---|---|---|---|
| 一般のLLM＋Excel | ○ | × | × | × | × | × |
| 脚本パックン | ○（AIが主役） | 手修正のみ（公開情報の範囲） | 不明 | 不明（PPM資料の出力が中心） | 約束（AI学習対象外・暗号化） | 記載なし |
| Creators Note | △（半自動） | △ | △ | × | 不明 | iPad／Mac |
| SUKETTO | × | × | × | 工程表の共有 | 不明 | × |
| **KOBAN** | △（部品として） | **○（中心）** | **○（中心）** | **○** | **○（端末で暗号化）** | **○** |

脚本パックンが売っているのは「AIで香盤を作る」部分で、そこはまさにLLMで置き換えられる部分である。KOBAN はそこで正面から競わず、作ったあとに起きることのすべてを引き受ける。利用者が脚本パックンや一般のLLMで最初の香盤表を作り、それを KOBAN に取り込んで回す、という使い方も歓迎する。そのために Excel と CSV の取り込みを最初の版から持つ。

## 7. 実現性

技術的には、v0.1 の判断どおり実現できる。台帳の中心（導出・追従・検査・配布）は通常のWeb技術で作れる。ただし、レビューで同期と権限の設計に致命的な穴が見つかっており、実装前に直す（`04`・`05`）。

台本本文の暗号化は、鍵の管理という新しい難所を持ち込む。鍵を失うと本文が読めなくなり、「データを失わない」原則とぶつかる。復旧コードと、作品メンバーへの鍵の受け渡しを設計に含める。暗号化するのは本文だけで、香盤表を動かす構造のデータ（柱・人物・撮影日）は暗号化しない。台帳としての機能は、本文が読めなくても動く。

LLMの利用は2通りに分ける。一つは、作品ごとに利用者が明示的に許可した場合だけ、本文を外部のLLMへ送って下書きを作る機能（既定は無効）。もう一つは、利用者自身のLLMから台帳へつなぐ接続口で、この場合に本文をどこへ送るかは利用者の契約と判断に委ねる。

## 8. 統合で生まれる機能（台帳の視点で再定義）

| # | 機能 | どの柱か |
|---|---|---|
| S1 | 台本・Excel・空の表のどれからでも、話数つきの台帳を起こせる | V1 |
| S2 | 改訂稿の取り込みで、変わったシーン・増えた人物・消えた小道具を一覧にし、影響する撮影日と日々スケまで示す | V2 |
| S3 | 香盤表の各印に根拠（台本の行・手入力した人・AIの提案）を持たせ、根拠のない印を目立たせる | V3 |
| S4 | 撮影日を組み替えたとき、NG日・拘束時間・移動・日照の矛盾と、日々スケへの影響を即座に示す | V2・V3 |
| S5 | 日々スケを配布し、更新時は差分を冒頭に添え、キャスト一人ひとりがスマホで自分の入り時間を読める | V4 |
| S6 | 誰がどの版を確認したかを集計し、未確認の人だけに再送する | V4 |
| S7 | 版の履歴から、任意の日の状態を開ける | V2 |
| S8 | 利用者のLLMから台帳を読み、変更を提案として送れる。提案は検査と承認を経て反映される | 接続口 |

## 9. やらないこと

- **AIによる生成の精度で競う。** そこはLLMの進歩で誰でも追いつく領域である。
- **予算・精算管理。** 日本の制作部は会計ソフトと Excel で持っており、台帳とのつながりが薄い。
- **3Dの配置図。** 2Dで十分である。
- **リアルタイムの共同編集。** 行単位の同期と上書き履歴で足りる。

## 10. 事業の見込み

料金と収益の前提は要件定義（`03` 第12章）に置き、ここでは考え方だけを示す。

課金の単位は、価値の大きさに合わせて「作品」と「会社」にする。変更と関係者が増えるほど価値が増すので、無料枠は作品の規模（撮影日数）で区切り、小さな自主短編は無料のまま使える。支払うのは制作会社で、請求書払いとインボイスに対応する。個人の助監督が自腹で払う前提は置かない。

v0.1 の「有料1,000人で月商約100万円、作品プラン50本併用で150〜200万円」は計算を誤っていた（正しくは約122万円で、税込・手数料前）。新しい料金での見込みは、無料利用者から有料作品・有料会社への漏斗として、`03` 第14章で一本の式にして示す。
