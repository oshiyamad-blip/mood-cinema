## 1. 結論

最も効く提案は三つある。一つ目は、最初の顧客を自主映画ではなく**縦型ショートドラマの量産現場**に絞り、データモデルに「話数」を今のうちに入れること。二つ目は、フェーズ1を**Web版だけ・課金なし**で出し、ストア申請と課金の実装をフェーズ2に送ること。浮いた2〜3週間を、Excel の香盤表の取り込みと集客記事に回す。三つ目は、同期を自前で作る前に、**既存の同期エンジンを1週間だけ試す**こと。フェーズ1で最も危険な工程の負担を下げられる可能性がある。

この三つは互いに支え合う。量産現場はExcelからの乗り換え需要が最も強く、課金より先に定着を確かめるべき相手だからである。

## 3. 各提案

### P1 最初の顧客を縦型ショートドラマの量産現場に絞る

**現状。** 主な顧客を「自主映画・短編、縦型ショートドラマ、小規模CM・MV、専門学校・大学」と並列に置いている（03 §3）。

**提案。** 公開から半年は、縦型ショートドラマの制作会社と、その現場の助監督・制作部を最初の顧客にする。自主映画と学校は無料の利用者として受け入れ続けるが、機能の優先順位と営業はショートドラマに合わせる。

**理由。** 自主映画の撮影は年に1〜2本で、香盤表を組む期間も短い。無料枠の作品1本で用が足りてしまい、課金に進まない。ショートドラマは月数十本を量産し、同じロケ地で複数の話をまとめ撮りするので、香盤表と総スケの作り直しが毎週起きる。手作業の負担が最も大きく、道具に払う理由が最も強い。検討（02 §2.4）でもプレイヤーは74社ほどで、営業先を数えられる規模である。

**変えること。** 02 §3.4 の事業規模の見積もりを、ショートドラマ制作会社への作品単位の課金を軸に書き直す。03 §3 のペルソナの先頭に「ショートドラマ制作会社の助監督」を置く。

### P2 データモデルに「話」を入れる

**現状。** 作品の下にシーンが直接ぶら下がる（04 §7.2）。連続ドラマの「作品」の数え方は未決のままである（03 §16、05 §14）。

**提案。** 作品の下に「話（エピソード）」の層を置き、シーンは話に属する形にする。単発の映画は「話が1つの作品」として扱い、画面では話の層を隠す。香盤表と総スケは、話をまたいでロケ地ごとに並べられるようにする。

**理由。** ショートドラマ（P1）も連続ドラマも、撮影は話数順ではなくロケ地順に組む。話をまたいだ香盤表が組めないと、量産現場では使えない。この層は、データが溜まってから足すと全行の移行が要る。最初から入れれば、列を1つ足す程度で済む。作品プランの数え方の未決も、「作品＝話の束」と決まって解ける。

**変えること。** `episodes` テーブル（作品ID、話番号、題、並び）を足し、`scenes` に `episode_id` を持たせる。シーン番号は「話番号-シーン番号」で一意にする。台本の取り込みは1話ずつ行い、取り込み先の話を選ばせる。香盤表の並びに「話→シーン順」を加える。

### P3 フェーズ1は Web 版のみ、課金なしで公開する

**現状。** フェーズ1の最後の2週（M6）で、個人プランの課金とストア申請を行う（04 §22、05 §7）。

**提案。** フェーズ1は Web 版（PWA）だけを、無料のベータ版として公開する。iOS・Android のストア版と課金は、配布リンクや共同編集が揃うフェーズ2で出す。支払い意思は、課金の代わりに「正式版の先行予約（価格を明示した事前登録）」で測る。

**理由。** フェーズ1の機能は、香盤表・総スケ・日々スケPDF・ショットリストで、どれもPCの大画面で行う作業が中心である。現場でスマホが要るのは閲覧で、それは PWA でオフラインまで賄える（基本設計の方式どおり）。ストア申請・審査対応・RevenueCat と Stripe の両系統・特商法の最終確認画面は、合わせると2〜3週間かかる。しかも価値の中心であるチームでの配布が無い段階では、課金しても転換率から学べることが少ない。浮いた期間は P4 と P8 に回す方が、定着と集客に効く。

**変えること。** 03 §13 のフェーズ1の到達点を「Web版で、助監督が1本の香盤表・総スケ・日々スケを作れる」に絞る。04 §22 の M6 を「Excel 取り込み・集客記事・先行予約ページ」に差し替える。05 §7（課金）はフェーズ2の詳細設計へ移す。Capacitor の採用は変えない。同じコードで、フェーズ2にストア版を出す。

### P4 Excel の香盤表の取り込みをフェーズ1に前倒す

**現状。** テンプレートからの取り込み（03 F4-6、F12-2）はフェーズ2である。フェーズ1の入口は台本の取り込みだけになっている。

**提案。** 既存の Excel の香盤表を読み込み、シーンと人物と印を起こす機能をフェーズ1に入れる。自社テンプレートの書式に加え、「見出し行を指定し、各列を『番号・柱・人物…』に割り当てる」汎用の取り込みを用意する。

**理由。** 想定顧客の大半は、すでに Excel で香盤表を作っている。乗り換えの最大の障壁は、今の作品を作り直す手間である。また、台本の自動解析は書式のばらつきで失敗しうる（03 §15 のリスク）。Excel 取り込みはその代わりの入口になる。データの形が決まっている分、台本解析より確実に動く。

**変えること。** 05 §9.4 で一元化した列定義を、取り込み側でも使う。列の割り当て画面を、取り込み確認画面（05 §8.3）の一形態として作る。

### P5 同期エンジンの既製品を1週間試してから自作を決める

**現状。** 行単位の最終更新優先、HLC、テーブルごとに生成する upsert 関数、勧告ロック、上書き履歴を自前で作る（04 §8、05 §5）。M5 に2週間しか割いていない。

**提案。** M1 の中で1週間、Supabase と組み合わせて使える既製のオフライン同期エンジン（PowerSync など、SQLite を端末側に持つ方式のもの）を試す。Capacitor の WebView と Web の両方で動くか、衝突時に負けた版を履歴に残す処理を足せるかを確かめる。満たせば採用し、満たさなければ今の設計で自作する。

**理由。** 同期は、データを失わないという最上位の原則に直結する。それなのに、設計の中で最も誤りが入りやすい部分である。性質テスト（05 §13.2）で守る設計にはなっているが、2週間で作り込むのは楽観的だ。既製品が条件を満たせば、自作の範囲は「上書き履歴の退避」と「作品単位の権限」まで縮む。1週間の試行で、どちらに転んでも判断材料が残る。

**変えること。** 04 §4 の技術選定の表に「同期エンジン：自作、または既製品（M1で判断）」の行を足す。05 §5 は、採用した場合の差分だけを書き直す。

### P6 「台本なしで始める」入口を作る

**現状。** 新規作品を作ると、台本の取り込み画面へ進む（05 §8.2）。香盤表が空のときの案内も「台本を取り込む」だけである（05 §8.5）。

**提案。** 新規作品のあとに「台本を取り込む」「Excel から取り込む（P4）」「空の香盤表から始める」の三択を出す。空から始めた場合は、香盤表の最下行に「シーンを足す」行を置き、番号と柱を打つだけで行が増えるようにする。

**理由。** 現場では、台本が画像の PDF でしか手に入らない、決定稿の前に香盤表を組み始める、という場面が珍しくない。取り込みに失敗した利用者が、そのまま離れる経路を残したくない。手で入れた行は、あとで台本を取り込めば改訂差分（フェーズ2）の仕組みで対応づけられる。

### P7 作品プランを月額から「作品ごとの買い切り」に変える

**現状。** 作品プランは ¥4,800/作品/月（03 §12）。

**提案。** 作品プランを「1作品 ¥9,800、準備から撮了後3か月まで（最長6か月）」の買い切りにする。量産現場（P1）向けには、月に作品を何本でも作れる会社プランを別に用意する。

**理由。** 制作会社では、道具の費用を作品の予算の一行として計上する。月額の継続課金は、作品が終わったあとの解約忘れが嫌われ、稟議も通しにくい。作品単位の買い切りは、海外でも SetHero が採っている（01 の出典に挙げた SetHero の料金説明 https://help.sethero.com/en/articles/1513627-how-do-the-pricing-plans-work ）。作品が終わったあとは閲覧専用で残す、という既定の設計（03 §12）とも相性が良い。

### P8 集客記事とテンプレートを公開前から出す

**現状。** 無料テンプレートと書き方記事は M6 で5本を出す（04 §22）。

**提案。** 開発と並行して、M1 から記事を週1本ずつ出す。最初の題材は検索の需要がはっきりしていて、日本語の良い記事が少ないもの（「香盤表の作り方」「香盤表テンプレート」「日々スケの書き方」「撮影スケジュールの組み方」「カット割り表のテンプレート」「絵コンテのテンプレート」）。各記事に Excel のテンプレートと、先行予約（P3）への導線を置く。

**理由。** StudioBinder の集客は、無料テンプレート記事による検索流入が半分以上を占める（01 §4）。検索で評価されるまでには数か月かかるので、公開と同時に始めても遅い。公開前に記事を出しておけば、公開日に先行予約の名簿を持って始められる。

### P9 版の履歴（「昨日の状態に戻す」）をフェーズ1で見せる

**現状。** 自動スナップショットを1日1世代・7世代まで端末に取り、復元は設定画面から新しい作品として行う（05 §4.7）。

**提案。** 作品一覧のカードのメニューに「版の履歴」を置き、日付ごとのスナップショットを、シーン数・人物数・撮影日数の差分つきで一覧にする。選ぶと「この版を新しい作品として開く」ができる。

**理由。** 仕組みはすでにあり、画面を一枚足すだけで済む。助監督が恐れるのは、総スケを大きく組み替えたあとで「元の方が良かった」となることである。戻れると分かっていれば、思い切って組み替えられる。データを失わないという原則を、利用者が目で確かめられる場所にもなる。

### P10 日々スケの簡易配布リンクをフェーズ1.5として切り出す

**現状。** 配布リンク（暗号化・既読つき）はフェーズ2で、フェーズ1は PDF を共有するだけである（05 §8.8）。

**提案。** フェーズ1の公開後すぐの小さな追加として、既読なしの配布リンクだけを先に出す。暗号化・有効期限・取り消しは基本設計（04 §10）どおりに作り、既読と名前選びは後から足す。

**理由。** 日々スケは前日の夜に何度も直る。PDF を作り直して LINE に貼り直す手間こそが、現場の一番の不満である。既読を外せば、Worker の API は作成・更新・取り消し・閲覧の4つで済む。この機能が、課金（フェーズ2）の前に使い続ける理由を作る。

### P11 台本解析の精度を、取り込み後の手直し回数で測る

**現状。** 解析の精度は、許諾を得たサンプル20本のゴールデンテストで測る（05 §13.1）。公開後の実際の精度を測る仕組みはない。

**提案。** 取り込み確認画面での手直し（結合・分割・番号の振り直し・話者の統合・行種別の変更）の回数を、台本の本文を含めずに件数だけ計測する（05 §12 の事象に追加）。手直しの多い書式の傾向を見て、判定規則を育てる。

**理由。** 20本のサンプルでは、実際の台本の書式の幅を覆いきれない。本文を送らずに件数だけを数えるなら、プライバシーの方針（04 §15）とも矛盾しない。

### P12 ロケ地・機材・撮影保険の送客で、課金以外の収益を作る

**現状。** 収益はサブスクリプションと作品プランだけである（03 §12）。

**提案。** ロケ地の画面からフィルムコミッションやロケ地紹介サービスへ、日々スケの準備物から機材レンタルへ、作品の設定から撮影保険へ、それぞれ案内を出し、提携先から送客の手数料を受ける。案内は、利用者の作業を妨げない控えめな位置に限る。

**理由。** 自主映画や学生のように課金しない利用者からも収益が生まれる。案内の先は、制作の現場が実際に必要とするものである。ただし交渉相手が多く、手間の割に額は小さい可能性がある。フェーズ2以降の検討とする。

## 4. 採らない方がよいと判断した案

検討したうえで、勧めない案も記しておく。

- **フェーズ1から AI のブレイクダウンを入れる。** 差別化にはなるが、台本を外部へ送る同意の設計と、誤抽出の扱いが必要になる。まず規則ベースの解析と手直しの体験を固めてからにする。
- **予算管理を早めに入れる。** CineFlo や StudioBinder にはあるが、日本の制作部は会計ソフトと Excel で予算を持っており、香盤表とのデータのつながりが薄い。
- **Shot Designer のような3Dの配置図。** 12年続く製品でも実装されていない。2Dで十分である（02 §3.1）。

## 5. 採用した場合の進め方

P1・P2・P3・P5 は互いに影響し、要件定義の段階から書き換えが要る。採用を決めたら、03 の要件定義書から順に改訂し、04・05 の該当箇所を追従させる。残りの提案は、どれも単独で採否を決められる。
