## 1. 背景と目的

撮影準備の中心にある香盤表は、一度作って終わりではない。台本の改訂、俳優のNG日の変更、ロケ地の差し替え、天候による撮影日の入れ替えのたびに、助監督は香盤表・総スケ・日々スケを作り直し、関係者に配り直している。最初の香盤表を作る作業は、いまや一般のLLMでも、AIで香盤を作る国内のサービス（脚本パックン）でもできる。しかし、作ったあとの変更を食い違いなく回し続ける仕組みは、Excel と手作業のままである。

本プロダクトは、撮影準備の正本となる台帳である。台本・人物・ロケ地・撮影日を一つの台帳に持ち、香盤表・総スケ・日々スケをそこから導出する。変更を取り込むと影響を示し、各情報の根拠を残し、矛盾を検査し、最新版を配って確認を集める。台本の本文は運営者にも読めない形で預かる。

目的は三つある。

1. 変更のたびに起きる作り直しと転記の漏れをなくす。俳優の呼び漏れのような、撮影日を失う事故を防ぐ。
2. 関係者全員が、いつも同じ最新版を見ている状態をつくる。
3. 制作会社が作品や会社の単位で支払う事業として成り立たせる。

## 2. 製品コンセプト

ひとことで言えば「台本が変わっても、香盤・スケジュール・日々スケが食い違わない」。

価値の柱は5つと接続口1つで、要件の優先順位はこの順に従う（詳しくは `02` 第4章）。

| 柱 | 内容 |
|---|---|
| V1 正本 | 香盤表・総スケ・日々スケを同じ台帳から導出し、食い違いを構造的に起こさない |
| V2 変更の追従 | 改訂・NG日・ロケ地・撮影日の変更を取り込み、影響を示し、版として残す |
| V3 根拠と検査 | 各印の根拠（台本の行・手入力した人・AIの提案）を残し、矛盾と抜け漏れを機械的に検査する |
| V4 配布と確認 | 日々スケを配り、更新の差分を添え、誰が確認したかを集める |
| V5 台本の秘匿 | 本文を学習・統計・改善に使わない。端末で暗号化し、運営者にも読めない |
| 接続口 | 利用者のLLMから台帳を読み、変更を提案として送れる |

## 3. 対象ユーザー

| ペルソナ | 役割 | 主な利用場面 | 利用端末 |
|---|---|---|---|
| 助監督（チーフ・セカンド） | 台帳の正本の管理者。香盤表・総スケ・日々スケの作成と更新、改訂の取り込み | 準備期間はPC、前日夜と現場はスマホ | PC、スマホ |
| 制作部（制作担当・進行） | 人物・連絡先・NG日・ロケ地の管理、日々スケの配布と確認の回収 | 準備期間、前日夜 | PC、スマホ |
| プロデューサー・制作会社の管理者 | 作品と会社の契約、メンバーの招待、進捗の把握 | 随時 | PC |
| 監督・撮影部 | 香盤表と日々スケの閲覧。フェーズ2以降はショットリスト・配置図 | 準備、現場 | スマホ、タブレット |

主な顧客は、縦型ショートドラマを量産する制作会社と、配信向け連続ドラマの助監督部・制作部である。従たる顧客は、改訂の多いCM・MVの制作会社である。自主映画・短編・学生作品は、無料枠の利用者として受け入れる。劇場公開の大規模商業映画は初期の対象外とする。

## 4. スコープ

### 4.1 やること
台帳（作品・話・シーン・要素・人物・ロケ地・撮影日）の管理。台本・Excel/CSV・空の表からの取り込み。縦書きの台本表示と改訂の取り込み・差分・引き継ぎ。根拠つきのブレイクダウン。香盤表、総スケ、日々スケの導出と編集。矛盾と抜け漏れの検査。日々スケの配布と確認の集計。版の履歴と復元。本文の端末暗号化。PDF/Excel の書き出し。作品メンバーと権限（フェーズ2）。ショットリスト・配置図・ビューファインダー・絵コンテ・現場モード（フェーズ2）。LLM の下書きと接続口（フェーズ2〜3）。

### 4.2 やらないこと
AI生成の精度で競うこと。予算・精算管理。脚本の執筆エディタ（取り込み専用）。正確なレンズデータベースを持つビューファインダー。3D配置図。リアルタイムの共同編集。台本の本文を使った解析の改善・統計・AI学習。

## 5. 用語

| 用語 | 定義 |
|---|---|
| 台帳 | 作品の正本となるデータの集まり。シーン・要素・人物・ロケ地・撮影日とその関係。香盤表などの表は台帳から導出する見え方である |
| 香盤表 | シーンを行、登場人物・衣裳・小道具などを列にしたマトリクス |
| 総スケ | 全撮影日のスケジュール。各撮影日にどのシーンをどの順で撮るかを示す |
| 日々スケ | 撮影日1日分のスケジュール。集合・場所・シーン順・出演者の入り・各部の準備事項を載せる。海外のコールシートに相当 |
| 話 | 連続ドラマ・ショートドラマの1話。作品の下の層で、シーンは話に属する。単発作品は話が1つの作品として扱い、画面では話の層を隠す |
| 根拠 | 台帳の情報がどこから来たか。台本の版と行の範囲、手入力した人、AIの提案、Excel の取り込み、のいずれか |
| 尺 | シーンが本編で占める長さ（秒）。任意入力 |
| 撮影見積 | シーンやカットの撮影にかかる時間（分）。段取りと本番を含む。総スケの時間割に使う |
| 改訂稿 | 台本の版。版名（準備稿・決定稿・色など）と改訂日を持つ |
| NG日 | キャスト・スタッフが出られない日 |
| 配布 | 日々スケを閲覧用のリンクで関係者に渡すこと。更新すると同じリンクの中身が新しい版になる |
| 確認 | 配布を受けた人が「見ました」を返すこと。版ごとに集計する |

## 6. 業務フロー

### 6.1 現状
助監督が台本を読み、Excel で香盤表を手入力する（最近は LLM や AI サービスに下書きさせることもある）。香盤表をコピーして総スケを作り、撮影日ごとに日々スケを作って PDF にし、LINE やメールで配る。台本の改訂、NG日の変更、ロケ地の差し替えのたびに、香盤表・総スケ・日々スケをそれぞれ手で直し、配り直す。どこを直したか、誰が最新版を見たかは、助監督の記憶と LINE の既読に頼っている。

### 6.2 目標
1. 台本・Excel・空の表のどれかから台帳を起こす。シーン・人物・ロケ地が根拠つきで抽出される。
2. ブレイクダウンを補うと、香盤表ができる。根拠のない印には印が付く。
3. 香盤表のシーンを撮影日に割り当てると総スケになる。NG日・拘束時間・重複は即座に検査される。
4. 撮影日を開くと日々スケができる。集合時刻と各部のメモを足して配布し、確認を集める。
5. 改訂稿が来たら取り込む。変わったシーン・増えた人物・消えた小道具と、影響する撮影日・日々スケが一覧になり、確認して反映する。
6. 反映した結果、日々スケが変わった撮影日には、差分を添えて再配布を促す。未確認の人だけに再送できる。
7. いつでも版の履歴から、前の状態を開ける。

## 7. 機能要件

優先度は MoSCoW（M=必須、S=重要、C=あれば良い、W=今回やらない）。フェーズは第13章のリリース計画に対応する。

### F1 作品・話・メンバー

| ID | 要件 | 優先度 | フェーズ |
|---|---|---|---|
| F1-1 | 作品を複数作成・切替できる。作品は題名・種別（映画/ショートドラマ/連続ドラマ/CM/MV/その他）・撮影期間を持つ | M | 1 |
| F1-2 | 作品の下に話を持てる（話番号・題・並び）。シーンは話に属し、シーン番号は話の中で一意。単発作品では話の層を画面に出さない | M | 1 |
| F1-3 | 作品の削除はゴミ箱経由のソフト削除とし、30日間復元できる。30日の起算はサーバーの時刻で行う | M | 1 |
| F1-4 | 作品全体を JSON でバックアップ・復元できる（復元は常に新しい作品として作る） | M | 1 |
| F1-5 | 作品にメンバーを招待できる。役割は管理者／編集者／閲覧者。作品の設定・削除・メンバー管理は管理者だけ | M | 2 |
| F1-6 | 閲覧者は香盤表・総スケ・日々スケを閲覧できるが、連絡先一覧と上書き履歴は見られない | M | 2 |

## 8. 非機能要件

| 分類 | 要件 |
|---|---|
| データ保全 | 利用者のデータを失わないことを最上位原則とする。削除はすべてソフト削除で、サーバー時刻で30日間復元できる。他の端末・他の人の変更で上書きされた版は、作品が存続する間すべて残す（同じ端末による連続した編集の途中経過は残さない）。自動処理（同期・改訂の取り込み・課金の降格）が本文を黙って消す経路を作らない |
| 台本の秘匿 | F10 のとおり。本文の平文は端末の外へ出さない（利用者が明示的に許可した AI 下書きと、利用者自身の接続口を除く） |
| 根拠 | 台帳のすべての印と抽出結果に根拠を持つ（F4-3） |
| オフライン | 閲覧・編集・PDF の出力は通信なしで動く。端末を正とし、クラウドは複製。復帰時に自動で同期する |
| 同期 | 行単位の最終更新優先とし、上書きされた版は履歴に残す。同じ行の二重作成が起きない ID 体系にする。1行の異常で他の変更の同期を止めない |
| 権限 | サーバーの内部処理を利用者が直接呼べない。作品の所有者・プランなどサーバーだけが決める値は、利用者が書き換えられない |
| 性能 | シーン300・列150・撮影日60の作品で、香盤表の表示が2秒以内、編集の反映が200ms以内。PDF の生成時間は試作で実測して目標を決める |
| セキュリティ | 通信は TLS。配布リンクは推測できない識別子と暗号化、有効期限、取り消しを持つ。連絡先は役割に応じて伏せる |
| 個人情報 | 個人情報保護法に沿う。利用目的の明示、第三者提供なし、海外リージョン利用時の情報提供、退会時の削除。外部送信規律（電気通信事業法）への該当を確認し、必要な公表を行う |

| 言語 | 日本語を第一とし、UI 文言は英語も同じ形で持つ |
| アクセシビリティ | 文字のコントラスト比4.5:1以上、部品の境界3:1以上（置かれた地の上で）。タッチ対象44px以上（現場用48px）。OS の文字サイズに追従する。色だけで意味を伝えない |

## 9. データモデル（概略）

```
Workspace
└─ Project（作品）
   ├─ Episode（話）: 番号, 題, 並び
   │   └─ Scene: 話内番号, 見出し, ロケ地, 時間帯, 屋内外, ペラ, 尺(秒), 撮影見積(分), 本文(暗号化)
   ├─ ScriptVersion（改訂稿）: 版名, 改訂日, 全文(暗号化), 行の索引
   ├─ Element（要素）: カテゴリ, 名前, 人物
   ├─ SceneElement（印）: シーン, 要素, 根拠{種別, 版, 行の範囲, 入力者, 日時}   ※(シーン,要素)で一意
   ├─ Person: 名前, 役名, 区分(キャスト/エキストラ/スタッフ), 部署, NG日 / 連絡先(別管理)
   ├─ Location: 名称, 住所, 座標, 利用可能時間
   ├─ ShootDay: 日付, 集合, 撤収予定 / 割り当て: シーン, 並び, 開始の固定
   ├─ CallSheet（日々スケの上書き分）/ Share（配布）: 版, 有効期限 / Ack（確認）: 人, 版, 日時
   ├─ Snapshot（版の履歴） / History（上書きされた版）
   └─ Shot・Blocking・Media・Storyboard（フェーズ2）
```

香盤表・総スケ・日々スケは独立したデータを持たず、台帳から導出する。

無料枠を撮影日数で区切るのは、台帳の価値が作品の規模と変更の頻度に比例するからである。小さな自主短編は無料のまま使え、量産や連続ドラマの現場は支払う理由がある。支払うのは制作会社で、個人の助監督が自腹で払う前提は置かない。AI 下書きの利用分は、原価に応じて有料プランに上限つきで含める（フェーズ2で決める）。

### 14.2 フェーズ2（課金開始から12か月）の漏斗

```
有料の作品数／月 = 新規作品数／月 × 無料枠を超える割合 × 作品プランへの転換率
月の売上        = 有料の作品数 × ¥9,800 ＋ 会社プランの契約数 × ¥29,800
```

| 変数 | 仮定 | 根拠と検証方法 |
|---|---|---|
| 新規作品数 | 月400本 | フェーズ1の実績から置き直す |
| 無料枠を超える割合 | 30% | フェーズ1の「撮影日6日以上」の比率で検証 |
| 作品プランへの転換率 | 25% | 先行予約からの実契約率で検証 |
| 会社プランの契約数 | 10社 | 先行予約10社のうち実契約に至る数で検証 |

この仮定では、有料作品は月30本で約¥29万、会社プランは10社で約¥30万、合計は月約¥59万（税込・決済手数料前）になる。税抜で約¥54万、Web 決済の手数料3.6%を引くと約¥52万である。大きくはないが、固定費（月約¥1万〜2万）に対しては十分に黒字で、少人数で回せる。仮定はフェーズ1の実績で置き直す。

## 15. リスクと対策

| リスク | 対策 |
|---|---|
| LLM の進歩で「香盤を作る」価値がさらに下がる | 生成で競わず、変更の追従・根拠・配布・秘匿に価値を置く。LLM はむしろ接続口で取り込む |
| 脚本パックンなど既存の競合が、追従や配布を足してくる | 先に量産現場に入り込み、改訂と配布の運用に組み込まれる。Excel・CSV の往復で乗り換えの壁を下げる |
| Excel 文化からの移行が進まない | Excel の取り込みと書き出しで往復を保証する |
| 台本書式のゆらぎで自動分割が失敗する | 規則解析と手直しを前提にし、手直しの件数だけを計測して規則を育てる（本文は集めない） |
| 暗号化の鍵を失い、本文が読めなくなる | 復旧コード、端末内の自動バックアップ、メンバー間の鍵の受け渡し。構造のデータは暗号化しないので台帳の機能は残る |
| 連絡先の漏えい | 配布の期限・取り消し・電話番号の伏せ、閲覧者に連絡先一覧を見せない |
| 作品の合間に解約され、継続しない | 量産現場には会社プランを、単発には作品プランを当て、月額の継続に頼らない |
| 支払意思が想定より低い | フェーズ1で先行予約と価格インタビューを行い、課金開始前に料金を見直す |
| 制作会社の経理に合わない | 請求書払いと適格請求書に対応する |
| ストア審査 | Apple の審査（Web を包んだだけと見なされる、アプリ内の退会）に備える。Google Play の個人アカウントは12人以上・14日間のクローズドテストが要るので、フェーズ2の日程に組み込む |
| 外部データへの依存 | 天気（非公式の JSON）・地図はなくても動く縮退を必須にする |
| 法務 | 電気通信事業法の外部送信規律、特定商取引法の表記（事業者情報の公開）を公開前に確認する |
